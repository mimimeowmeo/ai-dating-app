## 6. 回報

### 一句話總結
專案現在是一個 **monorepo**（一個 repo 裡放多個子專案）。之後前端、後端、共用套件都放在這裡，在根目錄用 `pnpm build`、`pnpm lint` 這類指令，就能一次處理全部。

### 檔案地圖
```text
ai-dating-app/
├── package.json          ← 根設定：pnpm 版本、Node 版本、統一指令
├── pnpm-workspace.yaml   ← 子專案在哪：apps/*、packages/*
├── pnpm-lock.yaml        ← （自動產生）每個套件的確切版本
├── turbo.json            ← 各指令的相依順序、快取
├── biome.json            ← lint + 格式化規則
└── .env.example          ← 環境變數範本
（之後會出現的資料夾）
├── apps/web              ← F3：Next.js
├── apps/api              ← F3：NestJS
├── packages/contracts    ← F7：自動產生的 API client
└── services/ai, ai-worker ← F3：Python（由 uv 管理，不歸 pnpm 管）
```

### 執行流程：在根目錄跑 `pnpm build` 時
```text
pnpm build
 → package.json 的 scripts.build = "turbo run build"
 → Turborepo 讀取 pnpm-workspace.yaml，找出所有子專案
 → 讀取 turbo.json：build 的 dependsOn 是 ["^build"]
     → 先 build packages/contracts（因為 web 和 api 依賴它）
     → 再平行 build apps/web 和 apps/api
 → 每個子專案執行它自己 package.json 裡的 build 指令
 → 輸出的內容（dist/、.next/）會被快取；程式碼沒改時，下次直接用快取
```

### 內容說明

**`package.json`（根目錄）**
```json
"private": true,
"packageManager": "pnpm@12.4.2",
"engines": { "node": ">=24 <25" },
```
- `private: true`：這個根專案不會被發布到 npm，也不會被誤發布。
- `packageManager`：固定 pnpm 版本。corepack 會照這個版本執行，所以每個人和 CI 用的 pnpm 都一樣。
- `engines`：Node 版本不符時，pnpm 會警告。

```json
"scripts": {
  "build": "turbo run build",
  "format": "biome format --write .",
  "check": "biome check ."
}
```
- `build`、`lint`、`test` 這些指令都交給 Turborepo，**由它去執行每個子專案裡同名的指令**。
- **前端類比**：就像父元件的 `onClick` 把事件分派給所有子元件，每個子元件用自己的 handler 處理。
- `format`、`check` 直接在根目錄執行，Biome 一次就能掃完整個 repo。

**`pnpm-workspace.yaml`**
```yaml
packages:
  - "apps/*"
  - "packages/*"
```
- 告訴 pnpm：`apps/` 和 `packages/` 底下的每個資料夾，都是一個子專案。
- 子專案之間可以互相引用，例如 web 可以寫 `"@heartlink/contracts": "workspace:*"`，直接使用本地的程式碼，不用發布到 npm。
- **為什麼不包含 `services/*`？** 那裡是 Python 專案，由 uv 管理，所以明確排除。

**`turbo.json`**
```json
"build": { "dependsOn": ["^build"], "outputs": ["dist/**", ".next/**", "!.next/cache/**"] },
"dev":   { "cache": false, "persistent": true }
```
- `^build` 裡的 `^` 代表「**我所依賴的套件**」。意思是：build 我之前，先 build 我依賴的套件。
- `outputs`：build 的產出放在哪裡。Turborepo 會快取這些檔案，輸入沒變就不會重新 build。
- **前端類比**：就像 `useMemo` 的依賴陣列，依賴沒變，就直接用上次的結果。
- `dev` 不快取，`persistent: true` 代表這是一個持續執行的服務（dev server），不會自己結束。

**`biome.json`**
- `vcs.useIgnoreFile`：直接使用 `.gitignore`，所以不會去掃描 `node_modules`。
- `files.ignoreUnknown`：Biome 不認得的檔案類型（例如 .md、.py）就略過，不報錯。
- `formatter`：2 格空格、每行最多 100 字元、雙引號。
- `linter.preset: recommended`：使用官方推薦的規則。
- `organizeImports`：自動整理 import 的順序。

**`.env.example`**
- 列出所有需要的環境變數，但只放假的值。每個人第一次使用時執行 `cp .env.example .env`，再填入真正的值。
- **前端類比**：跟 Next.js 的 `.env.local` 一樣。`NEXT_PUBLIC_` 開頭的變數會被打包進瀏覽器端的程式碼，**所以不能放秘密資訊**。
- 分成 PostgreSQL、Redis、MinIO、API、AI、Web 幾區，F2 的 Docker Compose 會讀這個檔案。

### 過程中遇到的狀況：pnpm 的供應鏈安全檢查
- 第一次安裝時，Biome 最新版 2.5.14 才發布不到一天，pnpm 12 **預設不會安裝發布未滿 1 天的版本**（`minimumReleaseAge`）。
- 如果被入侵的維護者帳號上傳了惡意版本，通常幾小時內就會被發現並撤下，等一天可以避開這段風險。
- pnpm 一開始自動在 `pnpm-workspace.yaml` 加了例外清單，等於繞過保護。我把例外清單**移除**，改用 7 天前發布的 2.5.13。
- 接著重新安裝時，pnpm 又發現舊的 lock 檔裡還記著 2.5.14，於是**拒絕安裝**。我刪掉 lock 檔重新產生，問題解決。這也證明了這層保護真的有效。
- 已經記錄為決策 D27。

### 這次學到的重點
1. **monorepo = 一個 repo 裡放多個子專案**，共用設定，也可以互相引用程式碼。
2. **pnpm 負責安裝和連結套件，Turborepo 負責依正確順序執行指令並快取結果**。兩個工具的分工不同。
3. **lock 檔一定要 commit**：它記錄每個套件的確切版本，確保大家安裝到的東西一模一樣。
4. **供應鏈安全**：不要急著安裝剛發布的版本；遇到工具自動加例外時，要先搞清楚它繞過了什麼。
5. `.env.example` 要 commit，`.env` 絕對不能 commit。
